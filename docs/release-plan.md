# 正式版与测试版更新计划

基础评估日期：2026-11-18；优先级更新：2026-11-20。首个正式版为 `1.0.0`，当前预览版本为 `1.1.0-beta.1`。本文件记录版本范围与验收条件，未实现功能不能因写入计划而视为完成。按功能成熟度推进交付。主题和性能测量并行，系统场景在候选版集中验收。

下一功能版本目标为 1.1.0。优先推进“素简／雾映”、纯净抽屉和贴边直角，并行建立性能基线。随后完成拖拽反馈、手动模式及首张音乐卡。爱发电前瞻版以两套主题和音乐卡为主要展示内容。具体待办见[开发计划](roadmap.md)。

## 版本号规则

首个正式版使用 **v1.0.0**。版本号按“主版本.功能更新.缺陷修复”递增：

| 形式 | 用途与示例 |
| --- | --- |
| `1.0.0` | 首个正式版 |
| `1.0.1`、`1.0.2` | 正式版的问题修复与兼容性维护 |
| `1.1.0` | 在 1.x 基础上增加功能；下一轮主题、性能优化、手动模式和音乐卡在此规划 |
| `2.0.0` | 将来有重大不兼容变化时再考虑；不按测试版数量自动升级主版本 |
| `1.0.0-beta.1`、`1.0.0-beta.2` | 1.0.0 正式发布之前的测试版，数字按序递增 |
| `1.1.0-beta.1`、`1.1.0-beta.2` | 下一目标正式版的测试，从 beta.1 重新编号 |

发布顺序：`0.1.0-beta.14` → `1.0.0-beta.1` → 必要后续 beta → `1.0.0` → 按需 `1.0.1`、`1.0.2` 等缺陷修复版；功能更新递增第二位，例如 `1.1.0-beta.1` 起，验收后 `1.1.0`。同一目标版本下 beta 早于正式版，不用正式版编号分发未经验证的新功能。

GitHub 标签/发布标题使用 `v` 前缀，例如 `v1.0.0`；工程和打包脚本的版本参数使用 `1.0.0`。已发布的 0.1.0-beta 系列标签和附件保留，不重命名、不覆盖。本地试用包通过打包参数指定版本，公开发布前统一工程、安装包、文档和标签。

## 首个正式版范围与验收

2026-11-18 用户明确要求 **v1.0.0 完成基本桌面整理功能**，包括普通多类型文件、文件夹与文件夹映射。此前仅以快捷方式版收口的范围已被取代。v1.0.0 已接入基本文件能力。自动回归和待完成的系统场景见[验证说明](validation.md)。

正式版必须补齐内容模型、通用文件操作、排序/多选、跨抽屉操作、备份与异常卸载保护，再完成真实系统验收。详细现状、最低行为和边界见[v1.0.0 基本功能清单](v1-basic-features.md)。后续主题、性能改进及手动模式进入 v1.1.0 规划。当前维护阶段优先处理数据丢失、启动失败和失控资源增长。

正式版不是商业收费版的同义词；本计划不加入授权、付费或承诺未验证的系统兼容性。

## 前瞻试用版与验收节奏

首轮本地试用先验证主题、明暗和系统切换、透明效果降级、隐藏标题的移动和恢复入口，以及贴边直角。音乐卡接入后形成爱发电前瞻候选版。

- **发布门槛**包括文件操作安全、旧数据升级、备份恢复、异常卸载和原路径重装。每个面向用户的候选包先做安装和冷启动冒烟检查，完整安装与升级矩阵使用干净的 Windows 环境验证。
- **验收周**集中覆盖 Explorer 重启、锁屏休眠、登录与延迟磁盘、多屏与 DPI、桌面共存及至少八小时资源趋势。统一归档环境、步骤、结果与缺口，后续按改动复测受影响场景。
- **后续试用功能**包括多抽屉合并为同一个窗口并按标签页切换，以及按用户设置的规则自动归位。各标签保留文件归属，归位规则先预览再启用。

## 性能基线与优先优化

beta.13 的一次既有会话约 13.5 分钟、54 个样本：平均 CPU 约 0.23%（按全部逻辑处理器归一化），最近工作集约 469 MiB、私有内存约 373 MiB。当时管理面板可见、一个抽屉、图标缓存四项。这是排查线索，不能视为标准基线，也不能从启动初期到界面加载后的差值直接认定泄漏。

1. 与主题开发并行测量，在启用毛玻璃、加入音乐卡前分别留存基线。固定发行版本与数据集，预热十分钟；区分管理面板显示、隐藏，抽屉展开、折叠、交互，覆盖 1/5/20 个抽屉及不同内容数量。
2. 采集 CPU 时间、工作集、私有内存、托管堆/分配/GC、GDI/USER/总句柄、线程、磁盘读写、抽屉重建次数与 UI 延迟。现有日志没有的字段需按低开销原则扩展；昂贵的堆/分配诊断仅在排查时启用。
3. 比较预热后至少一小时同类空闲阶段，以及验收周内八小时候选版进程的变化；对悬停、滚动、缩放、面板反复开关做固定次数对比。
4. 优先调查隐藏面板的内容和预览刷新、重复绑定/集合生成、每次渲染的新 `RenderTargetBitmap`、动画上传中的像素缓冲与 GDI 对象分配、图标缓存生命周期及备份扫描。源码位置只是候选，按测量排序，不预先宣称瓶颈。
5. 不使用周期性强制 GC、清空工作集等方式制造任务管理器数字下降。保留必要缓存，报告延迟、CPU 与内存的取舍。

建议候选目标：固定场景中预热后的私有内存与分配量下降；八小时无持续句柄或活对象增长；游戏场景本应用 CPU 不高于普通模式，空闲不连续生成动画帧。具体 MB/百分比目标在可重复基线完成后确定，不承诺未经测试的数值。

## 游戏模式的可行设计

可行性高。它只减少栖格自己的后台和视觉工作，不保证游戏 FPS 一定增加，也不修改其他进程的优先级、内存或反作弊环境。

| 模式 | 栖格行为 |
| --- | --- |
| 正常 | 按需绘制，保留动画与正常刷新；静止抽屉不持续重绘 |
| 节能 | 缩短/关闭非必要动画，降低动画更新频率，合并内容/状态刷新，限制缓存保留，推迟可延期的完整扫描和定时备份 |
| 游戏 | 默认暂停非必要动画和预览更新；根据用户选项隐藏或冻结抽屉的视觉交互；面板隐藏时停止其预览刷新，进一步延后后台可选任务 |

前瞻版先提供设置和托盘中的手动开关。卡片阶段之后再开发自动进入，使用前台窗口、覆盖显示器工作区和用户指定游戏等信号，不仅依赖进程名称。播放器、演示和远程桌面可能全屏，需可排除；不注入游戏、不扫描游戏内存。手动游戏模式优先于自动判断，并清楚显示当前状态和原因。

游戏时可以不渲染被全屏覆盖的抽屉，但切到另一个显示器或 Alt-Tab 后必须及时可用。停止视觉功能不能通过退出程序并批量归还文件实现；保留分组和收纳状态。

正在执行的收纳/归还、写盘提交、完整性校验与中断恢复不被强行暂停或取消。文件监视保留或记录脏标记，退出游戏后合并补同步；完整扫描、配置变更备份可推迟但要有最大等待期限。用户主动备份和恢复保持可用，恢复/移除前安全备份仍必须执行。

当前没有全应用统一的固定帧率：抽屉主要在变化时生成表面，动画计时器约 8 ms，拖动采样约 16 ms。需按动画/拖动/面板刷新分别调节，不能承诺“全局设成 30 FPS”就解决资源问题。

## 动态调节的可行设计

本项安排在卡片阶段和手动模式稳定之后。第一版只做正常与节能之间切换，游戏识别作为独立条件。CPU 使用系统总体负载和本进程 CPU，内存压力采用可用物理内存与提交余量；不高频枚举全部进程，也不把“空闲内存少”单独等同于压力。GPU 压力采集成本与兼容性另评估，不作为首版依赖。

- 初始试验参数：每 3–5 秒低频采样，使用 15–30 秒平滑窗口；持续高负载或低内存余量时降档。CPU 高于约 80% 持续 15 秒、低于约 50% 持续 30 秒作为实验起点，正式阈值由不同核心数和场景数据校准。
- 降档与恢复使用不同阈值，至少保持 30–60 秒，防止频繁切换；严重内存压力可更快收缩可重建缓存。
- 用户操作临时提高响应预算；不得在拖动、文件事务或恢复中途切换破坏状态的策略。压力解除后逐步恢复，积压任务限速补做，避免恢复瞬间再次占满资源。
- 允许关闭动态调节、固定正常或固定节能，显示“因系统负载进入节能”等原因。默认先保守，测试版验证有效后再决定是否默认启用。

## 包体实测与优化边界

beta.14 的本地自带运行时 x64 包，2026-11-16 按文件长度统计；不包含运行后产生的 `QigeData`，也不等于文件系统实际分配空间。

| 项目 | 大小 |
| --- | --- |
| 安装器下载 | 44.96 MiB |
| 便携 ZIP 下载 | 62.96 MiB |
| 解压后程序文件合计 | 140.55 MiB |
| 主程序集 `Qige.dll` | 481.5 KiB，约 0.47 MiB |
| 随包 docs 与 assets | 约 0.80 MiB |

主要体积是 .NET/WPF 运行库，例如 CoreLib、PresentationFramework、PresentationCore 和原生渲染库。压缩包体不会自动降低运行内存。

优化顺序：检查语言卫星资源（仅保留产品支持语言并验证回退）、排除无用交付资产、比较安装压缩参数；另评估可选的依赖 .NET Desktop Runtime 小包，明确系统需另外安装运行库。默认自带运行时包继续保留，不能把首次安装成本隐去。

WPF 的裁剪、Native AOT 和单文件不作为默认捷径：反射/XAML 兼容性需独立验证；单文件可能仍会解包且不保证更小或更省内存。不能手删看似没调用的运行库 DLL。当前文档/图片不足 1 MiB，删截图不是主要收益来源。另列数据目录占用及备份/历史副本，不能为压缩程序体积删除用户恢复资料。

## 卸载与重新安装的当前行为

| 情况 | 当前结果 |
| --- | --- |
| 只重新下载安装器 | 不改变已有内容 |
| 正常退出并归还全部后卸载 | 可用的托管快捷方式归还原个人桌面，分组/布局等配置与历史数据留在原安装目录的 `QigeData`；同名冲突不覆盖，需先解决 |
| 应用仍运行时直接卸载 | 安装器检测应用生命周期/数据占用并阻止，提示先退出归还 |
| 任务管理器强杀、崩溃或异常终止后卸载 | 卸载器发现未归还内容或待处理恢复状态时会停止，重新打开原路径应用并完成归还后可继续 |
| 保留数据后在原路径重装，同一用户使用 | 默认重新读取原 `QigeData`，恢复分组和设置；启动会按原分组重新收纳桌面入口，存在冲突时进入恢复处理 |
| 改路径重装、换账户/桌面路径，或删除数据目录 | 新位置不会自动发现旧数据；当前没有跨目录数据导入流程，不能保证自动延续。保留旧目录并先按原环境归还/恢复，避免直接合并两套数据 |

当前卸载器主要保护数据目录，不是独立恢复工具；已卸载的目标软件不会因为归还快捷方式而重新安装。正常归还的桌面排列由 Windows 决定。

正式版验收继续覆盖静默卸载、同名冲突、离线盘、权限失败、原路径重装和异常退出后的恢复。
